# 标签搜索性能：213 万补全候选验证

本次调整将标签补全改为构建时生成二进制索引，原生平台由常驻后台 isolate 持有索引，界面只接收少量搜索结果和当前需要的标签元数据。打开空搜索框时可以先读取小型 bootstrap，展示默认候选；完整索引在后台准备，不再要求界面持有全部候选对象和全量显示名、分类映射。

在本轮 Linux 环境中，真实 **2,132,126 条补全候选**的引擎初始化，四轮中位数从旧实现的 **9.639 秒**降到新索引首次建立缓存的 **1.952 秒**，已有缓存时为 **1.236 秒**。本次使用四轮交替顺序、共十二个独立桌面 AOT 进程，记录每轮实际顺序及全部原始结果。它们不能直接视为手机上的等待时间或应用启动时间。原始结果、查询返回值和校验信息见 [完整基准 JSON](tag-search-benchmark.json)。

## 数据与测量口径

- 使用项目实际 Git LFS 资源 `assets/danbooru_completion.zip`，没有用合成数据替代性能数据集。
- 去重后共 **2,132,126 条补全候选**，包括翻译与别名；此数量不等同于唯一英文 tag 数。
- 使用 **Dart 3.10.8 native AOT** 编译 [基准工具](../tool/benchmark_completion.dart)。SDK 来自项目 CI 固定的 Flutter 3.38.9。
- 旧实现、新索引冷路径、新索引暖路径分别运行在**独立进程**中，前一个实现的 Dart 堆不会留在后一个实现中。
- 共执行 **4 轮**，每种模式各测 4 次独立进程初始化。第 1、3 轮为 `legacy → index-cold → index-warm`，第 2、4 轮为 `index-cold → index-warm → legacy`；索引组内始终先建立缓存，再测暖路径。
- 每个进程在初始化完成后对每个查询测首次调用，再测 **2 次重复调用**。下文报告四个样本的中位数和实测最小值、最大值；这些范围不是置信区间、P95 或稳定性承诺。
- 交替顺序用于减少固定执行顺序造成的混杂；主机负载、温度和频率未受控，不据此判断旧单轮数据的偏差方向。
- **没有刷新操作系统 page cache**。冷路径指“没有已解压的应用索引缓存”，不代表物理磁盘缓存也是冷的。
- 初始化计时从读取补全输入前开始，到构建完成为止；不包含进程创建、Flutter 框架启动、页面绘制、键盘弹出或网络图片加载。
- 内存对比统一采用 `rssAfterInitializationBytes`，即**初始化完成后的进程 RSS**。JSON 同时保留系统报告的峰值等原始字段，但表中不混用峰值与初始化后 RSS。
- 查询基准直接调用引擎，不经过服务层结果缓存。因此重复查询数据也不是 LRU 缓存命中耗时。

本轮结果文件生成于北京时间 **2026 年 11 月 16 日 00:44:42**。具体运行环境、每轮顺序与各模式进程 ID 均保存在 JSON 中。

## 完整初始化耗时

单位为毫秒。阶段表采用四轮中位数，冷、暖路径都包含磁盘读取和内容校验；不能把单独的 header 构造耗时当作完整加载耗时。各阶段分别汇总，其中位数之和不必等于总耗时中位数。

| 阶段 | 旧实现 | 新索引首次建立缓存 | 新索引使用已有缓存 |

| bootstrap 读取与解析 | — | 0.061 | 0.104 |
| ZIP 读取 | 18.393 | 22.840 | — |
| 旧 JSON 解码、去重、排序、records 与全量映射构建 | 9,612.491 | — | — |
| ZIP SHA-256 校验 | — | 299.246 | — |
| CRC 校验、解压与索引构造 | — | 317.033 | — |
| 已解压缓存读取 | — | — | 66.260 |
| 已解压索引 SHA-256 校验 | — | 1,208.792 | 1,155.921 |
| 缓存写入并 flush | — | 76.225 | — |
| 缓存索引构造 | — | — | 0.035 |
| **完整初始化总计，中位数** | **9,639.126** | **1,952.450** | **1,235.600** |
| 完整初始化范围，最小–最大 | 8,933.485–11,166.295 | 1,849.331–2,194.218 | 1,160.658–1,406.612 |

暖路径的主要成本已经变为读取完整索引后的 SHA-256 校验。基准保留这一步，防止将完整性检查从性能数据中省略。冷路径还计入了缓存写入；原生后端可以在写入完成前发出 ready，因此这里的冷路径数值覆盖了更完整的工作量。实际实现见 [原生后端](../lib/completion_backend_io.dart)。

bootstrap 为 **1,454 字节**。全部索引进程的读取解析范围为 0.058–0.120 毫秒，仅是本机读取解析这份小文件的时间，**不是手机 UI 首帧、点击到键盘出现、或点击到建议可见的实测时间**。它的意义是让空搜索框的默认候选不再依赖完整索引初始化完成。

## 同口径内存对比

以下仍统一比较初始化完成后的 RSS，汇总四个独立进程样本。

| 实现 | RSS 中位数，字节 | RSS 中位数，MiB | RSS 范围，MiB |
|---|---:|---:|---:|
| 旧实现 | 1,619,431,424 | 1,544.410 | 1,526.227–1,970.293 |
| 新索引首次建立缓存 | 273,389,568 | 260.725 | 260.598–260.754 |
| 新索引使用已有缓存 | 124,209,152 | 118.455 | 118.379–118.613 |

按各模式中位数计算，初始化后 RSS 分别减少约 **83.1%** 和 **92.3%**。首次建立缓存的进程仍可能保留解压、校验和临时缓冲区，因此高于直接读取二进制的暖路径；这张表不是垃圾回收后稳定占用的保证。

JSON 同时保留每个进程的峰值 RSS，但没有将峰值与初始化后 RSS 混用于百分比计算。`currentRss` 与 `maxRss` 是系统分别采样的原始值；判断长期占用仍需要设备侧测量。

## 结果一致性与顺序边界

基准比较了空查询、英文前缀、中文、中间子串、四种短符号和无匹配，共 **10 组查询**，并在 **4 轮**中逐轮与同轮旧实现结果比较。两种新索引模式在每一轮均满足：

- 候选数与旧实现一致：**2,132,126**。
- 每组返回结果的主排名序列一致：**最早匹配位置升序，再按 score 降序**。
- 匹配位置按 Dart `String.indexOf` 的 **UTF-16 code units** 计算，保留 value 与 insert value 取较早位置的规则。
- 所选精确标签查询的显示名、分类与旧实现一致。

生成器采用 `(-score, value)` 固定候选 ID；旧实现对相同 score 的排序未保证稳定。因此，**匹配位置与 score 都相同的别名可能采用不同的确定性顺序**，不承诺每个等分结果的排列和旧版完全相同。

上述一致性结论只覆盖这 10 组查询及所选精确标签查找，不构成任意标签、任意查询均与旧版相同的证明。大小写规则统一使用固定的 [Unicode 15.0 简单小写映射表](../scripts/completion_lowercase.json)，Python 构建器、原生与 Web 查询、UI 预处理和缓存键使用同一份逐 scalar 映射。`İ` 映射为 `i`，`ΟΣ` 映射为 `οσ`；仍区分 final sigma 与普通 sigma，也保留组合标记，不执行 case folding 或 NFC 规范化。这个约定保持原 Python 3.12 生成的二进制索引内容与数据哈希不变，并补齐 Dart VM 旧 Unicode 表缺失的映射。它统一了 Deseret、Cherokee 和 Georgian 等字符在不同运行时中的行为，不宣称所有 Unicode 输入均保留旧 VM 的结果。

独立的小型回归覆盖大小写规范化、中文别名优先、分类 `0`、跨 NUL 边界、结果上限及损坏 header，见 [completion_index_test.dart](../test/completion_index_test.dart)。另外在 Dart VM 与 dart2js 编译后的 Node.js 执行路径中验证跨运行时查询语义，见 [completion_web_check.dart](../test/support/completion_web_check.dart)；这项检查不包含浏览器 UI 或页面加载性能测量。

| 资源 | 字节数 | 十进制 MB |

新 ZIP 比旧 ZIP 增加 **2,760,703 字节，约 2.76 MB**；加上 bootstrap 后，运行时补全资源净增约 **2.762 MB**。旧 JSON ZIP 通过 Git LFS 保存，作为生成输入；新索引 ZIP 和 bootstrap 在构建时生成，已加入 `.gitignore`，应用打包时仍包含这两个派生资源。这一构建方式不改变上表的应用资源字节数或本轮性能结果。生成流程见 [build_completion_index.py](../scripts/build_completion_index.py)。

原生平台另外使用约 **117.8 MB** 的解压缓存，以免后续启动重复解压。缓存以索引内容哈希命名并在读取时校验；系统清理临时目录或缓存不匹配时，需要重新建立缓存。此空间成本应与内存下降、加载时间改善一起评估。

**Web 存在不同边界。** 当前 [Web 后端](../lib/completion_backend_web.dart) 没有原生 isolate 和上述磁盘缓存路径。查询扫描会分段让出事件循环，但首次资源校验、ZIP 解压仍在浏览器主线程执行，首次加载仍可能造成卡顿。本报告没有测浏览器实机交互，也没有把原生后台加载的收益直接套到 Web。

## 重现方法

在仓库根目录执行，使用 Flutter **3.38.9 / Dart 3.10.8** 与 Python 3。Git LFS 只需下载原始 JSON ZIP，并确认它是实际内容而非指针文件。首次执行 `flutter pub get`、`flutter test` 或 `flutter run` 之前，先用 Python 生成索引 ZIP 和 bootstrap：

```bash
git lfs pull --include="assets/danbooru_completion.zip"
python scripts/build_completion_index.py
CI=true flutter --suppress-analytics pub get

dart compile exe tool/benchmark_completion.dart -o /tmp/danbooru-completion-benchmark
/tmp/danbooru-completion-benchmark \
  --mode compare \
  --rounds 4 \
  --repetitions 2 \
  --output /tmp/danbooru-completion-benchmark.json

CI=true flutter --suppress-analytics test --no-pub test/completion_index_test.dart
```

CI、Release 与 Web 部署会在 Flutter 步骤前自动执行索引生成。每周同步提交源数据后，下一次构建会从更新后的原始 ZIP 重建两个派生资源；本地更新源数据后也应重新执行生成命令。生成文件无需提交到 Git 或 Git LFS。

`compare` 默认执行 4 轮，可用 `--rounds 1` 到 `--rounds 20` 调整。每轮为每种模式各创建一个独立子进程，交替安排旧实现与索引组的先后顺序，并用临时二进制缓存连接同轮的冷、暖两次运行。暖路径只在同轮冷路径成功后执行，避免将前一轮残留缓存作为成功样本。也可通过 `--mode legacy`、`--mode index-cold`、`--mode index-warm` 分别执行；后两种可用 `--cache /path/to/completion-cache.bin` 指定同一缓存。`--source`、`--index`、`--bootstrap` 可以指定待比较的实际资源。

本文的 schema version 2 JSON 在 `rounds` 中保留十二个独立进程的完整结果、每轮实际执行顺序和一致性检查，在 `summary` 中保留各模式的中位数与最小、最大值；查询样本、重复调用、校验身份和测量边界也一并保存。之后若修改候选内容、索引格式、查询算法或校验策略，应重新产生相应结果，避免将本次样本当作新版本的实测值。
