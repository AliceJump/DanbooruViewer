# 标签搜索性能：213 万补全候选验证

本次调整将标签补全改为构建时生成二进制索引，原生平台由常驻后台 isolate 持有索引，界面只接收少量搜索结果和当前需要的标签元数据。打开空搜索框时可以先读取小型 bootstrap，展示默认候选；完整索引在后台准备，不再要求界面持有全部候选对象和全量显示名、分类映射。

在本轮 Linux 环境中，真实 **2,132,126 条补全候选**的引擎初始化，从旧实现的 **9.688 秒**降到新索引首次建立缓存的 **2.287 秒**，已有缓存时为 **1.204 秒**。这是同一主机上的单轮桌面 AOT 基准，不能直接视为手机上的等待时间或应用启动时间。原始结果、查询返回值和校验信息见 [完整基准 JSON](tag-search-benchmark.json)。

## 数据与测量口径

- 使用项目实际 Git LFS 资源 `assets/danbooru_completion.zip`，没有用合成数据替代性能数据集。
- 去重后共 **2,132,126 条补全候选**，包括翻译与别名；此数量不等同于唯一英文 tag 数。
- 使用 **Dart 3.10.8 native AOT** 编译 [基准工具](../tool/benchmark_completion.dart)。SDK 来自项目 CI 固定的 Flutter 3.38.9。
- 旧实现、新索引冷路径、新索引暖路径分别运行在**独立进程**中，前一个实现的 Dart 堆不会留在后一个实现中。
- 每种模式的初始化只测 **1 次**。每个查询在初始化完成后测首次调用，再测 **2 次重复调用**。没有将这些数据包装成多轮均值、P95 或稳定性承诺。
- **没有刷新操作系统 page cache**。冷路径指“没有已解压的应用索引缓存”，不代表物理磁盘缓存也是冷的。
- 初始化计时从读取补全输入前开始，到构建完成为止；不包含进程创建、Flutter 框架启动、页面绘制、键盘弹出或网络图片加载。
- 内存对比统一采用 `rssAfterInitializationBytes`，即**初始化完成后的进程 RSS**。JSON 同时保留系统报告的峰值等原始字段，但表中不混用峰值与初始化后 RSS。
- 查询基准直接调用引擎，不经过服务层结果缓存。因此重复查询数据也不是 LRU 缓存命中耗时。

本轮结果文件生成于北京时间 **2026 年 11 月 15 日 23:37:48**。具体运行环境与各模式进程 ID 均保存在 JSON 中。

## 完整初始化耗时

单位为毫秒。表中的冷、暖路径都包含磁盘读取和内容校验；不能把单独的 header 构造耗时当作完整加载耗时。

| 阶段 | 旧实现 | 新索引首次建立缓存 | 新索引使用已有缓存 |
|---|---:|---:|---:|
| bootstrap 读取与解析 | — | 0.133 | 0.072 |
| ZIP 读取 | 182.006 | 19.061 | — |
| 旧 JSON 解码、去重、排序、records 与全量映射构建 | 9,506.102 | — | — |
| ZIP SHA-256 校验 | — | 306.533 | — |
| CRC 校验、解压与索引构造 | — | 768.400 | — |
| 已解压缓存读取 | — | — | 45.807 |
| 已解压索引 SHA-256 校验 | — | 1,132.599 | 1,157.737 |
| 缓存写入并 flush | — | 60.208 | — |
| 缓存索引构造 | — | — | 0.314 |
| **完整初始化总计** | **9,688.116** | **2,286.960** | **1,203.945** |

暖路径的主要成本已经变为读取完整索引后的 SHA-256 校验。基准保留这一步，防止将完整性检查从性能数据中省略。冷路径还计入了缓存写入；原生后端可以在写入完成前发出 ready，因此这里的冷路径数值覆盖了更完整的工作量。实际实现见 [原生后端](../lib/completion_backend_io.dart)。

bootstrap 为 **1,454 字节**。上表的 0.072–0.133 毫秒仅是本机读取解析这份小文件的时间，**不是手机 UI 首帧、点击到键盘出现、或点击到建议可见的实测时间**。它的意义是让空搜索框的默认候选不再依赖完整索引初始化完成。

## 同口径内存对比

| 实现 | 初始化后的 RSS，字节 | 初始化后的 RSS，MiB |
|---|---:|---:|
| 旧实现 | 1,621,966,848 | 1,546.828 |
| 新索引首次建立缓存 | 273,149,952 | 260.496 |
| 新索引使用已有缓存 | 124,203,008 | 118.449 |

在这一次运行中，初始化后 RSS 分别减少约 **83.2%** 和 **92.3%**。首次建立缓存的进程仍可能保留解压、校验和临时缓冲区，因此高于直接读取二进制的暖路径；这张表不是垃圾回收后稳定占用的保证。

旧实现初始化阶段记录的峰值 RSS 为 **1,884,573,696 字节**，但没有拿该峰值去计算上面的百分比。`currentRss` 与 `maxRss` 是系统分别采样的原始值，JSON 中的新路径二者存在很小的采样差异；判断长期占用仍需要设备侧测量。

这里所有查询都在该进程的引擎初始化完成后执行。旧实现的空字符串查询本身很快，但此前仍须完成全量 JSON 和映射加载；不能用空查询的 0.024 毫秒推断旧版首次点开搜索框没有等待。

新实现先按有序索引查找前缀；候选不足时保留中间子串搜索，以维持原有搜索能力。子串路径在后台扫描紧凑字节数据并定期让出事件循环。当前测量中的中间子串、右括号和无匹配仍比常见前缀慢，不能统一宣称所有搜索都是常数时间。代码见 [补全索引](../lib/completion_index.dart)。

## 结果一致性与顺序边界

基准比较了空查询、英文前缀、中文、中间子串、四种短符号和无匹配，共 **10 组查询**。两种新索引进程均满足：

- 候选数与旧实现一致：**2,132,126**。
- 每组返回结果的主排名序列一致：**最早匹配位置升序，再按 score 降序**。
- 匹配位置按 Dart `String.indexOf` 的 **UTF-16 code units** 计算，保留 value 与 insert value 取较早位置的规则。
- 所选精确标签查询的显示名、分类与旧实现一致。

生成器采用 `(-score, value)` 固定候选 ID；旧实现对相同 score 的排序未保证稳定。因此，**匹配位置与 score 都相同的别名可能采用不同的确定性顺序**，不承诺每个等分结果的排列和旧版完全相同。

独立的小型回归还覆盖 `İ`、希腊 `Σ`、Deseret 补充平面字符的 Dart 小写语义、中文别名优先、分类 `0`、跨 NUL 边界、结果上限及损坏 header。相关测试见 [completion_index_test.dart](../test/completion_index_test.dart)；这组 11 项引擎测试在记录本次结果时全部通过。

## 磁盘与平台权衡

| 资源 | 字节数 | 十进制 MB |
|---|---:|---:|
| 旧 JSON ZIP | 27,917,762 | 27.918 |
| 新二进制索引 ZIP | 30,678,465 | 30.678 |
| bootstrap | 1,454 | 0.001454 |
| 原生平台解压后的索引缓存 | 117,837,380 | 117.837 |

新 ZIP 比旧 ZIP 增加 **2,760,703 字节，约 2.76 MB**；加上 bootstrap 后，运行时补全资源净增约 **2.762 MB**。旧 JSON ZIP 通过 Git LFS 保存，作为生成输入；新索引 ZIP 和 bootstrap 在构建时生成，已加入 `.gitignore`，应用打包时仍包含这两个派生资源。这一构建方式不改变上表的应用资源字节数或本轮性能结果。生成流程见 [build_completion_index.py](../scripts/build_completion_index.py)。

原生平台另外使用约 **117.8 MB** 的解压缓存，以免后续启动重复解压。缓存以索引内容哈希命名并在读取时校验；系统清理临时目录或缓存不匹配时，需要重新建立缓存。此空间成本应与内存下降、加载时间改善一起评估。

**Web 存在不同边界。** 当前 [Web 后端](../lib/completion_backend_web.dart) 没有原生 isolate 和上述磁盘缓存路径。查询扫描会分段让出事件循环，但首次资源校验、ZIP 解压仍在浏览器主线程执行，首次加载仍可能造成卡顿。本报告没有测浏览器实机交互，也没有把原生后台加载的收益直接套到 Web。

## 重现方法

在仓库根目录执行，使用 Flutter **3.38.9 / Dart 3.10.8** 与 Python 3。Git LFS 只需下载原始 JSON ZIP，并确认它是实际内容而非指针文件。首次执行 `flutter pub get`、`flutter test` 或 `flutter run` 之前，先用 Python 生成索引 ZIP 和 bootstrap：

```bash
git lfs pull --include="assets/danbooru_completion.zip"
python scripts/build_completion_index.py
CI=true flutter --suppress-analytics pub get

dart compile exe tool/benchmark_completion.dart -o /tmp/danbooru-completion-benchmark
/tmp/danbooru-completion-benchmark \
  --mode compare \
  --repetitions 2 \
  --output /tmp/danbooru-completion-benchmark.json

CI=true flutter --suppress-analytics test --no-pub test/completion_index_test.dart
```

CI、Release 与 Web 部署会在 Flutter 步骤前自动执行索引生成。每周同步提交源数据后，下一次构建会从更新后的原始 ZIP 重建两个派生资源；本地更新源数据后也应重新执行生成命令。生成文件无需提交到 Git 或 Git LFS。

`compare` 模式会依次创建三个独立子进程，并用临时二进制缓存连接冷、暖两次运行。也可通过 `--mode legacy`、`--mode index-cold`、`--mode index-warm` 分别执行；后两种可用 `--cache /path/to/completion-cache.bin` 指定同一缓存。`--source`、`--index`、`--bootstrap` 可以指定待比较的实际资源。

本文的 JSON 汇总保留了本轮三个独立进程的完整结果、查询样本、重复调用、校验身份和测量边界。之后若修改候选内容、索引格式、查询算法或校验策略，应重新产生相应结果，避免将本次样本当作新版本的实测值。
