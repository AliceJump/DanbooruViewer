# 网络与媒体使用说明

## 选择网络方式

从图库右上角进入 **设置 → 网络与代理**。应用提供四种模式：

| 模式 | 行为 |
| --- | --- |
| 进程环境 | 使用启动进程的 HTTP_PROXY/HTTPS_PROXY/NO_PROXY 等环境设置；不是系统 PAC 自动检测 |
| 直连 | 不指定应用级代理；设备已有的 VPN/TUN 路由仍由系统处理 |
| HTTP | 所有应用读取通过填写的无认证 HTTP 代理，HTTPS 使用 CONNECT |
| SOCKS5 | 通过无认证 SOCKS5 代理；目标域名交给代理解析 |

主机和端口分开填写，例如 `127.0.0.1`、`10808`。端口对应的协议必须与代理软件的监听设置一致。该默认地址只是表单初值，不会自动打开手动代理。

`127.0.0.1` 指正在运行应用的设备。Android 上填写它表示手机本机；若使用电脑提供的局域网代理，应填电脑的实际局域网地址和允许该设备访问的监听端口。

当前版本不支持需要用户名/密码的代理或 PAC 脚本，设置中不保存代理凭据。Web 由浏览器决定代理，应用无法修改浏览器的代理或 CORS 规则，因此只显示说明和连接检查。

## 设置生效与故障反馈

保存设置会取消旧连接，使新请求使用新配置。图片缓存仍可复用；重新加载的资源走当前网络设置。

- 手动代理连接失败时不会退回直连。
- TLS 证书验证始终开启；证书错误、代理错误、超时、权限状态与限流应分别处理。
- 已保存配置损坏时保留原文并提示重新保存，不静默改变网络方式。
- 设置写入失败时不启用新路由。应用会显式恢复上次确认的值；只有平台确认写回成功，才视为恢复完成。普通重新读取可能仍返回 Android 原生内存中的失败值，不能作为恢复依据。网络配置尚未确认恢复时暂停连接，确认并重新保存成功后恢复；其他收藏字段的保存问题不会使已确认的网络路由失效。
- API 和 CDN 分开诊断，便于判断“帖子列表能开但图片不能开”的情况。检查结果不包含账号、密码或完整请求参数。
- GET 的临时错误会有限重试，并遵守有限截止时间和 Retry-After；刷新失败保留已显示作品。

匿名访问受到的站点权限限制不能靠代理解决。当前应用还没有站点账号/API key 配置。

## 媒体与保存

图片、Ugoira 和文件保存使用统一网络服务。原生视频先经该服务缓存，再交给平台播放器播放本地文件；首次播放需等待下载，这是为了让视频遵守相同代理策略。

| 平台 | 保存和播放行为 |
| --- | --- |
| Android / iOS | 图片与视频分别保存到相册；系统首次使用可能询问相册权限 |
| macOS | 使用平台可用的相册与播放器能力；用途描述和 release 网络权限随应用提供 |
| Windows / Linux | 保存到 Downloads 下的 DanbooruViewer 目录；无内置视频后端时可用系统播放器打开已缓存本地文件 |
| Web | 图片使用浏览器可用的数据提供器；保存交给浏览器，受站点 CORS 与浏览器下载策略约束 |

批量保存是前台队列。窗口中显示每项结果，取消会中止当前下载并停止后续项；重试只处理未完成项。关闭结果后保留未完成项的选择。它不宣称支持后台跨重启恢复。

Web 保存需要在浏览器内形成文件缓冲，单次保存设有大小上限；超过上限会提示打开原链接下载。Ugoira 也有压缩包、帧数与解码预算，超限会显示错误，不无限扩大内存。

Ugoira 压缩包在读取过程中限制为 64 MiB，整个 ZIP 的实际解压输出限制为 256 MiB，最多接收 502 个文件；帧元数据单独限制为 1 MiB。逐帧解码另有限额：单帧 16 百万级像素（16 × 1024 × 1024），总计 64 × 1024 × 1024 像素；宽高任一边不得超过 GIF 能表示的 65,535。这些是各阶段的输入与输出限额，应用峰值内存还包含解码、GIF 编码和界面开销。支持普通 stored/deflate ZIP；加密、多卷和 ZIP64 包会提示不支持。本地 ZIP 保存同样先转换为 GIF，再写入目标文件。

PNG 帧内部的压缩数据也会先验证实际输出：每帧不得超过其尺寸、位深和隔行方式所需的扫描行大小，同一动图累计不得超过 256 MiB。预检只保留 32 KiB 解压历史，核对长度、Adler 与数据块 CRC，再将已验证的图像、调色板、透明度和 gamma 数据交给解码器；GIF 不使用的文本、物理尺寸及 APNG 元数据不会传入。16 位 PNG 样本会转为 GIF 使用的 8 位通道。帧的实际格式限于 PNG、JPEG、WebP、BMP，不能仅改扩展名启用其他格式的解压路径。

JPEG、WebP 和 BMP 也会在解码器分配内存之前预检，单帧与整段动图的剩余像素预算同时生效，解码器自身的 `maxPixels` 也显式设置为该剩余额度。JPEG 核对完整标记结构、尺寸、分量和采样，按完整 MCU 填充、每个系数四字节保守计算，预算为 128 MiB；锁定的新版使用较小的 16 位系数存储，普通基线 JPEG 还可按行带解码。支持单帧 8 位 Huffman DCT 的普通和渐进 JPEG；重建必要的 Adobe 颜色变换及有限读取的 EXIF 方向，不把原始附加元数据交给解码器。WebP 核对画布、每个动画帧矩形与内部 VP8/VP8L 的实际尺寸，只将已经验证的首帧和透明度数据交给解码器，维持原有的首帧转换行为。BMP 限制调色板条目数并验证其实际字节范围、颜色掩码和完整像素行；支持普通未压缩和 bitfields 布局，RLE、内嵌 JPEG/PNG 等当前解码器未实现的 BMP 布局会明确报错。

无损 WebP 和压缩 ALPH 另有编码表预算，不能只靠图像尺寸推断分配量。首帧预检最多允许 64 个实际使用的 Huffman 组、4,096 个编码组编号范围，以及 524,288 个保守估算的表条目；估算包含扩展表段、packed 表和未使用组的临时代码长度表。预检只解码不允许再递归的变换／分组辅助图，预检与正式解码两次辅助像素累计限为 8 × 1024 × 1024。普通无损图和压缩透明度仍可转换；超过这些额度的合法复杂 WebP 也会明确提示超限。这些限额针对 ZIP 内帧的 GIF 转换，普通 WebP 浏览继续使用 Flutter 图像解码。JPEG 扫描次数在预检时限制为 100，与锁定解码器一致。

Web 动图查看与保存共用后台转换任务，转换期间仍可操作界面。每次运行一个任务，运行中与等待中的任务合计最多 4 个、ZIP 输入合计最多 64 MiB；超出时提示稍后重试。开始加载转换组件后设有 90 秒截止时间，取消保存或切换网络设置会停止对应任务。组件加载失败可重试，不会改为在界面线程执行完整转换。

原生端一次只读取、转换一份 ZIP。其他查看或保存任务排队等待，获得名额后才下载或读取文件，避免网格中多张动图同时解压；已有 GIF 缓存不必等待。取消排队任务不会读取来源。已开始的编码仍在后台 isolate 中完成后检查取消状态，再释放下一项，不会把仍在运行的 isolate 当作已停止。

Web 缓存随浏览器会话保存在内存中，最多保留 300 个对象，按最近使用顺序淘汰；删除与清空同时释放文件和索引。这是对象数量限制，不是总字节容量限制。原图必须成功解码首帧才替换预览；失败时保留预览并提供重试。

## 验证边界

本地假代理/HTTP 服务与 Flutter 测试可以验证路由、取消、错误处理和交互；它们不能替代目标设备上的真实 VPN、相册权限、硬件视频解码和系统外部播放器测试。发布记录应分别注明这些结果。

PNG 预检和转换支持低位深、16 位及 Adam7，包括存在空扫描 pass 的 1×1、1×8 窄图。`image 4.13.1` 和 `archive 4.7.1` 精确锁定；升级时必须复核 WebP 内部接口、解码预算和直接写入受限输出的解压契约。ZIP 与 PNG 使用 `Inflate.lazy` 逐块驱动，预算在每次字面量或回溯写入时生效，不先缓冲完整压缩块。
